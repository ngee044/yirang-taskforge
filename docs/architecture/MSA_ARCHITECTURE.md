## 1. 현재 적용 프로파일

실재 토폴로지와 ADR의 기준은 [SAD](../SAD.md)입니다. C++ 워커와 REST API는 실행 책임으로 나뉘며 Go/Python/JS는 동일 bounded context의 대안 구현입니다. 언어별 포트폴리오 비교를 위해 별도 프로세스·이미지를 가지므로 서비스 수가 도메인 수를 뜻하지 않습니다.

| 관심사 | 현재 구현 | 제약·근거 |
|---|---|---|
| 접수·조회 | API 3종 중 선택 | 같은 REST 계약, 구현 편차는 [API A](../API.md)에 명시 |
| 실행 | TaskForgeWorker | whitelist만 실행, API 프로세스에서 작업 실행 안 함 |
| 통신 | SQS FIFO + Redis 문서 + S3 객체 | API↔워커 동기 RPC 없음 |
| 데이터 | Redis 상태 공유 | 아래 소유권 예외를 명시적으로 적용 |
| 배포 | 서비스별 Dockerfile·Compose | 독립 이미지이나 계약 호환은 함께 검증 |
| 관측성 | 각 언어 Logger·health/readiness | 통합 추적 백엔드·메트릭 플랫폼 미도입 |
| 외부 진입 | API 직접 노출 | gateway/BFF·인증·테넌트 경계 미구현 |

## 2. 경계와 데이터 소유권

새 프로젝트·도메인은 modular-monolith-first를 기본으로 하고 독립 배포·팀 소유권·부하·장애 격리의 이점이 입증될 때 서비스를 추출합니다. 파일 크기나 엔티티 수만으로 분리하지 않습니다. 다른 서비스의 내부 소스나 SDK 모델에 직접 의존하지 않고 계약으로 연결합니다.

본 프로젝트의 공유 Redis는 database-per-service 원칙의 **명시적 예외**입니다. API는 최초 queued 문서를 기록하고 이후 상태 전이는 워커가 소유합니다. task_catalog는 워커가 게시하고 API는 조회합니다. 이 예외를 일반적인 공유 DB 권장으로 확대하지 않습니다. Redis/SQS 간 원자성은 없고 TTL 이후 중복 메시지에 대한 상태 가드도 사라집니다.

## 3. 계약과 신뢰성

[API](../API.md)의 REST/SQS/Redis 스키마가 기준입니다. 계약 필드 변경은 세 API와 워커, 요구사항·테스트·RTM에 미치는 영향을 함께 검토합니다. 직접 SQS 생산자에 대한 신뢰 경계는 REST 검증보다 넓으므로 필드 검증과 접근 권한을 별도로 고려합니다.

at-least-once 소비는 중복에 안전해야 하며 백오프와 jitter는 유계 예산으로 적용합니다. 상태 조회·저장 실패를 성공으로 숨기거나 ACK해서는 안 됩니다. 현행 기준선의 ACK 결함은 [T-005](../task_list.md)에서 시정합니다. 외부 호출 timeout 규범은 유지하며 워커 Redis의 API 제약을 미충족으로 기록합니다.

파일 DLQ·Redis 터미널 가드는 exactly-once나 원자적 멱등성을 제공하지 않습니다. outbox·saga·idempotency-key 저장소·circuit breaker는 현재 미도입이며 도입이 필요하면 실패 모델과 계약을 먼저 정의합니다. 현행 결함 수정에 이런 구성요소를 자동으로 추가하지 않습니다.

## 4. 수명주기·운영

기동은 필수 설정 검증 → 의존성 연결 → 소비/서빙 순서입니다. 종료는 신규 요청·소비 중단 → 진행 중 처리 drain → 연결·스레드 정리 순서입니다. 시그널 핸들러에서 Logger, mutex, 객체 해제를 직접 수행하지 않습니다. CppToolkit 종료 시그니처는 [모듈 가이드](../module_usage_guide.md)를 확인합니다.

API `/healthz`와 `/readyz`는 생존과 의존성 준비를 구분합니다. readiness는 전체 시간 예산 안에서 종료하고 외부 응답에 내부 예외를 노출하지 않습니다. Docker worker의 60초 유예는 설정값이며 모든 workload의 종료 상한을 검증한 결과가 아닙니다.

## 5. 확장 시 검토할 원칙

| 제안 | 채택 전 조건 |
|---|---|
| 인증·JWT/mTLS·테넌트 | 사용자·서비스 신뢰 경계와 데이터 소유권 |
| gateway/BFF | 클라이언트 계약 조합·공통 정책의 실제 필요 |
| outbox/saga | 원자성·보상 요구, 저장소 선택, 장애 재처리 설계 |
| 분산 추적 | 전파할 trace/correlation 스키마, 저장·비용·민감정보 정책 |
| 독립 서비스 추가 | 경계·소유권·배포/확장 이득, 단계적 전환과 롤백 |

현재 작업과 확장 제안은 [task_list](../task_list.md), [SaaS 제안](../NEXTJS_SAAS_TASK_LIST.md)에서 분리합니다. 문서 작성·감사 절차는 [ISO_MSA_CONVENTION](../ISO_MSA_CONVENTION.md)을 따릅니다.
