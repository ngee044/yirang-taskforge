## 1. 적용 범위와 원칙

문서는 프로젝트 `docs/`에 저장하고 Git 형상 관리에 포함합니다. 프로젝트별 지침의 포트폴리오 예외가 전역 docs 제외 규칙보다 우선합니다. 추적성은 최우선이며 모든 구현·시험 주장을 코드 또는 실제 실행 근거로 확인합니다. 규범 요구사항과 구현 부족을 분리하고 부족에 맞춰 규약을 완화하지 않습니다.

시스템의 네 실행 서비스 규모에 맞춰 평면 문서 체계를 사용합니다. 별도 `docs/system/`, `docs/services/`, `docs/adr/`는 현재 필수 산출물이 아니며 ADR은 SAD 안에 기록합니다. 구현되지 않은 서비스·계약·성능 목표를 사실처럼 쓰지 않습니다.

## 3. 식별자와 메타데이터

문서 시작에 문서 ID·버전·기준·최종 수정일·대상 커밋·상태를 둡니다. 새 문서는 작성일도 기록합니다. 날짜는 실제 날짜·기존 이력으로 확인하며 승인자·검토자를 추정하지 않습니다.

| 종류 | 규칙 |
|---|---|
| 문서 | `YTF-종류-001`; 기존 ID 보존 |
| 요구사항 | 기존 `FR-JOB-01`, `FR-WRK-01`, `NFR-REL-01`, `CON-01` 체계 보존 |
| 시험 | `TC-IF-01`, `IT-01`; 삭제·통합해도 참조 관계 유지 |
| 설계 결정 | `ADR-01` 등 SAD 내 ID |
| 개선·결함 | `T-001`, `SPR-001` |

상태는 Draft(초안), Active(현재 참조), Superseded(대체됨), Deferred(범위 밖 보류)를 사용합니다. Active는 사용자 승인이나 리뷰 통과를 뜻하지 않습니다. 승인 기록은 실제 확인된 경우에만 별도 기재합니다. 버전은 표현 수정 patch, 내용 추가 minor, 구조 변경 major로 올리고 짧은 변경 이력을 남깁니다.

## 4. 양방향 추적과 검증

RTM은 요구사항 → SAD 절/ADR → 실제 file:line 및 심볼 → STP 케이스를 연결합니다. 역방향에서도 모든 케이스의 요구사항이 일치해야 합니다. 없는 파일·함수·테스트를 연결하지 않으며 테스트 부재는 `없음` 또는 `계획`으로 적습니다. 자동화·수동 실측·정적 리뷰를 구분하고 계획 ID의 존재를 PASS로 간주하지 않습니다.

문서 갱신 시 헤더 기준 커밋과 인용 행을 대조합니다. 과거 실패·수정 이력을 본문에 계속 덧붙이지 않고 현재 상태로 본문을 갱신하며 이력 표에 변경 사실만 남깁니다. 결과가 서로 다르면 실행 시점·커밋·조건을 분리합니다.

## 5. 변경 절차

1. 코드·계약·실행 결과로 영향받는 요구사항과 문서를 판정합니다.
2. SRS/SAD/API의 규범 변경과 STP/RTM/SPR의 증거를 함께 갱신합니다.
3. 별도 문서 감사에서 ID·링크·코드·테스트의 실제 존재와 단언 범위를 확인합니다.
4. 승인된 작업 범위의 리뷰·테스트 후 문서와 관련 코드를 커밋합니다. 사용자 요청 없이 커밋·PR을 만들지 않습니다.

서비스 추가·인증·과금·저장 구조 변경 등 컨셉 확장은 별도 요구 확정 뒤 문서화합니다. 일반 버그 수정과 문서 현행화에 불필요한 재승인 절차를 만들지 않습니다.
